# Detailed expectations

## Why are we doing PLG monetisation strategy

When people pay for a product, it proves they're getting value. Monetisation and value are closely linked - it's our strongest signal of product-market fit.

Last year, Sales received $3M in funding to create a Sales-led approach which doesn't align with the Forma Design strategy for product-led growth, but it is Autodesk's comfort zone. This squad (Monetisation) exists to prove we should approach funding differently next time - a self-serve motion with a sales layer on top, not the reverse.

Strategic planning happens between now and June. A clear strategic narrative with executive buy-in and early wins will matter.

**The goal is to prove the motion works, not to hit specific targets.** We've set $1M for the full year and 250 conversions by the end of June as stretch targets to provide meaningful direction and get things moving. Success is demonstrating that self-serve conversion is viable.

### 1. Monetisation strategy

**What**: Define comprehensive strategic foundation for PLG monetisation motion.

**Key activities**:
- Clearly articulated destination (consider visualising the experience)
- Current state assessment of the business from a PLG monetisation point of view
- Detailed description of the user:
	- Ideal vs target user definition

	- Clear articulation of how subscription only models hit a ceiling (you need new features to stay still, let alone increase pricing)

Use 'more likely than not' criteria where velocity doesn't allow statistical significance. Optimise for easy conversion wins early - start with users already getting value.

### 2. System-level value definition

**What**: Define what outcomes are worth paying for and build solutions using native capabilities and extensions.

**Key activities**:
- Identify the outcome(s) we want to support that represent the minimum worth paying for
- Create solutions using three layers:
	- **Native capabilities**: What Forma provides out of the box
	- **First-party extensions**: Extensions we build to fill gaps (where we don't currently provide system-level value)
	- **Third-party extensions**: Partner-built solutions (e.g., Testfit, capacity study tools)
- Define scope clearly: what outcome(s) are we targeting, and what combination of native + extensions delivers that value
- Create the ideal user / use case concentric circles model showing focus and relative priorities
- Package existing value before building new features - think of recipes where ingredients are native, first-party, and third-party extensions

**Expectations**: Be opinionated about scope. Identify specific outcomes that justify payment and build the solution around them. Example: Daniel's capacity studies work could be a specific use case. The question is: what is the minimum viable system-level value that justifies paying?

### 3. Trial experience and user journey mapping

**What**: Create clear map of all key flows from getting started to conversion, with a point of view on what good looks like.

**Key activities**:
- Map complete journey: visit -> log-in -> trial -> conversion
- Document current state at each stage (baseline metrics)
- Define what good looks like at each stage
- Identify key drop-off points and hypotheses for why
- Map upgrade triggers and upgrade-to-conversion flow
- Focus on understanding what value people are willing to pay for

**Current state (from recent analysis):**
- Trial to paid conversion rate: ~0.005 (extremely low)
- Current payment flow: 6 screens (too complex)
- Key drop-off: Workflow 3 -> 4 transition (only 0.007 of trial users reach this)
- Current pricing: $700-$1000 (arbitrary, not data-driven)

**Expectations**:
- Have a clear map of all flows with defined success metrics
- Strong point of view on what good looks like at each stage
- Test the hypothesis that Workflow 4 is required to justify paying - is there a different version that provides enough value, or can users justify paying earlier in the flow?
- Focus on easy wins first: users already getting value from the tool
